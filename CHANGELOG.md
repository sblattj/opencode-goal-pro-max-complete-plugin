# Changelog

## 1.0.1 — 2026-09-08

- **New: the session's native Todo list is drawn from the goal plan.** While a plan exists the plugin rewrites the arguments of the model's *own* `todowrite` call in `tool.execute.before`, so the host performs exactly one write and the checklist every client renders **is** the plan: one row per action in plan order, content `a3 · rebuild dist` (the action id, ` · `, and the title bounded to 120 characters), and a plan past 20 actions ending in one counted `+N more actions — /goal status` row. The status map exists to stop the native `[✓]` asserting something the plugin's own evidence gate refuses — a `done` action becomes `completed` only once it is verified, a `done` action without a passing verdict mirrors as `in_progress` with ` — needs claim/evidence/verdict`, and a `blocked` action mirrors as `in_progress` with ` — BLOCKED: <reason>`, which is what the host's own todo contract asks for. Rows the model wrote itself are **kept**, below the plan rows, at most 10 of them and each bounded to 120 characters; nothing of the model's is silently deleted, and the tool result names how many were kept and how many the cap trimmed. `todowrite({todos: []})` is the refresh idiom and it is a redraw, never a delete: with a live plan it re-emits the projection and leaves the kept rows alone, with no live plan it re-emits the last mirrored rows or the terminal snapshot taken when the goal ended, and only in a session that never mirrored anything does an empty call reach the host as an empty list. A stale mirror is nudged at most **three** times per goal run — `Todo panel is stale — call todowrite({todos: []}) once; the plan is copied into it for you.` — shared across the auto-continue block and `goal_action_update`'s result, and `/goal resume` refunds the budget in full. `/goal stop`, `/goal clear` and a genuine completion each hand the list back in one line, because the mirror is one-way and the rows outlive the goal.
  - **New option `mirrorTodos`: `"plan"` (default) or `"off"`.** `"off"` restores 1.0.0 exactly: all three `todowrite` hooks return before touching anything, every prompt surface that mentions the mirror is silent, and `goal_plan_set`'s, `goal_action_update`'s and `todowrite`'s descriptions are the stock bytes — the `<existing_todos>` offer below is skipped along with the host read that produces it, so an `"off"` instance makes no `session.todo` call at all. The option is static and instance-wide by construction, so it cannot introduce cross-session skew.
  - **There is no "adopt" mode.** A session that already has native todo rows when `/goal set` runs gets them *described* back to the model once, in an `<existing_todos>` block on the goal's first continuation, with the instruction to either record them as the plan through `goal_plan_set` — rewritten as falsifiable claims — or ignore them. The read is best-effort and read-only: nothing is adopted, `goal.mirror.extra` starts empty, and a failing or absent host call is logged and skipped rather than blocking `/goal set`.
  - **The Goal panel becomes an exception list while the mirror is on**, because the Todo section is already showing the plan: unverified `done` actions first, then `blocked`, then `in_progress`, each group in plan order, and `pending` actions are not repeated. A `done` action without a verdict gains the same ` — needs claim/evidence/verdict` suffix on its panel line that its mirrored row carries, and the progress line gains ` · todo mirror fresh (5)`, ` · todo list stale`, or ` · mirror drift (7≠5)` when the panel's own live read of the host's list disagrees with the payload. Under the exception list `+N more` counts only the exception rows the 12-row cap dropped, over the **published** actions rather than the whole plan, so a server-capped plan cannot promise rows the payload does not carry. A payload with no `plan.mirror`, or one whose state is `off`, renders exactly as it did in 1.0.0.
  - **`metadata.goal` payload is now `v: 3`, adding two keys: `plan.mirror` and `plan.actions[].verified`.** `plan.mirror` carries `state` (`"fresh"`, `"stale"` or `"off"`), `rows` and `extra` (how many rows the last mirrored write held and how many of those were the model's own), and `at` (when that write landed, `0` for never). `verified` is the server's own CEV verdict on each published action — `done` **and** a claim **and** evidence **and** `verdict: "pass"` — and it exists because a consumer cannot re-derive it: `claim` and `evidence` are goal-private prose that never go on the wire, and `goal_plan_set` accepts a `done` action with a passing verdict and no ledger (only `goal_action_update` enforces the gate), so `status` plus `verdict` renders exactly that action as finished. The Goal panel now reads the flag rather than inferring it, which is what puts such an action back in the exception list with its ` — needs claim/evidence/verdict` suffix, agreeing with the mirrored todo row and the progress count that already named it unverified. Every v2 key is still written and both keys are purely additive. Skew warning, unchanged in shape from the v1→v2 one: the two halves are registered separately (`opencode.json` and `tui.json`), and the panel never reads `v` at all, so a 0.11.0 panel against a v3 payload simply lists every action and shows no mirror suffix, and the current panel against a v2 payload does the same. Upgrade both halves together.
  - **Two new hooks: `tool.execute.after` and `tool.definition`.** The freshness stamp lives in the *after* hook because only that hook proves the host actually wrote the list — between the two hooks the host decodes the arguments and asks for permission, and either can abort the call, so a mirror stamped fresh for a write that never landed would suppress the very nudge that repairs it. `tool.definition` appends a static paragraph to the builtin `todowrite` description telling the model what the tool now does in a goal-bearing session; it is never gated on goal state, because the hook carries no session id. `scripts/verify.mjs` requires both, so the hook surface it checks is now eleven names. A host that does not know `tool.definition` simply never fires it.
  - **The `todowrite` description suffix is stamped at most once per object.** The `tool.definition` hook returns early when the description it was handed already carries the mirror paragraph, so a host that re-triggers the hook against the same output object — or a second registration of this plugin in one directory — cannot double it. OpenCode 1.18.29 rebuilds the description object on every `ToolRegistry.tools()` call, so this is defensive rather than a fix for an observed host; it is pinned by a unit that stamps one object twice and by a mutation anchor that deletes the guard.
  - **Seven hazards are documented rather than fixed**, in [`docs/compatibility.md`](docs/compatibility.md#todo-mirror): the suffixed `todowrite` description reaching goal-less sessions in the same project, `todowrite: "ask"` turning every refresh into a permission modal, hosts where `todowrite` is denied (the mirror never becomes fresh, so the panel reads stale for the whole run and the nudge self-suppresses), another plugin's `tool.execute.before` overwriting the mirror with no way to detect it, the host's second and hookless `todowrite` implementation, `/undo` not rewinding todos, and one deliberate departure from the host's one-`in_progress` convention. The same document records the transcript bubbles — which the mirror reaches through the `args` rewrite rather than through a plugin slot, so on 1.18.29 they show the mirrored rows and `npm run smoke:todo-safety` re-measures that every run — and that `priority` is wire-only in the TUI.
  - **The published type declarations carry the whole surface.** `index.d.ts`: `GoalSidebarStatus.v` becomes `3`, `plan.mirror` (`{ state: "fresh" | "stale" | "off"; rows; extra; at }`) and `verified: boolean` on every published action join `GoalSidebarStatus`, `mirrorTodos` joins `GoalPluginOptions`, and `tool.execute.after` and `tool.definition` join `GoalPluginHooks`. `tui.d.ts`: `GoalPanelModel` gains an optional `mirror` (`state`, `rows`, `extra`, `liveTodoCount`, `drift`), and `goalPanelModel` gains a second parameter — `goalPanelModel(raw, options?: { liveTodoCount?: number })`. That parameter is **optional**, so a 1.0.0 call site that passes only the payload still typechecks and simply renders no drift comparison. Reading a payload is likewise unchanged; only code that *constructs* a `GoalSidebarStatus` literal has to grow the three new required fields, since that type describes what the server writes. One deliberate asymmetry between the two files: the panel's `mirror.state` is declared `string` rather than the server's three-value union, because the panel forwards whatever state the payload carried — a newer server can invent one — and it stands the progress suffix and the drift comparison down for a state it does not recognise, while still treating the mirror as active. Both files are typechecked as a consumer sees them, under NodeNext and Bundler resolution, by `npm run type:check`.
  - **The packed type contract exercises the 1.0.1 surface, not just the 1.0.0 one.** The `npm run type:check` fixture now sets `mirrorTodos: "plan"` in its `satisfies GoalPluginOptions` object with a `@ts-expect-error` negative case for an invalid value, calls `tool.execute.after` and `tool.definition` beside `tool.execute.before`, reads `plan.mirror.state` and `plan.mirror.rows` off a `GoalSidebarStatus`, and calls `goalPanelModel` both with and without its new options argument — so a declaration that stops compiling for a consumer fails the gate instead of waiting for the next reader.
- **New: two real-host smokes and a benchmark for the mirror.** `npm run smoke:todo-mirror` boots a real `opencode serve` against a mock model and asserts the plan is redrawn over a divergent list, with two controls — the same run under `mirrorTodos: "off"`, and a session with no goal — plus the SQLite row order and survival across a restart of the serve process. `npm run smoke:todo-safety` is the destructive half, and every assertion in it is about rows **surviving**: an empty `todowrite` arriving after `/goal stop` or after a genuine completion must re-emit the last mirrored rows rather than wipe the list, and the same call in a session that never had a goal must still clear it. Both need the `opencode` binary on `PATH` and a freshly bundled `dist/`, and neither is in `release:check`, because that binary is not a dev dependency. `scripts/bench-todo-mirror.mjs` measures the metric the design set: the number of distinct persistent checklists the sidebar renders, target one, under `"plan"` against an `"off"` control.
- **Unchanged: the identifier policy, and the state file version.** No new wire identifier and no new state path. `STATE_FILE_VERSION` is deliberately **not** bumped — a mismatch is rejected rather than migrated, so a bump would refuse every existing record; instead the mirror record is normalised on load, and a goal written before 1.0.1 comes back with an empty, never-mirrored one. The part metadata key, the plugin id, the log `service` field and both legacy state paths keep their historical `opencode-goal-plugin` strings, per the standing rule below.

## 1.0.0 — 2026-09-07

1.0.0 is the first release under the name `opencode-goal-pro-max-complete-plugin`, and it changes no code behaviour from 0.11.0 — the only edits to `src/` since that version are two comments. What is new is everything around the runtime: the rename itself (with the wire and state identifiers deliberately left on the historical `opencode-goal-plugin` string, so an upgrade keeps its goals and its in-flight sessions), the verification process now written down in [`docs/verification.md`](docs/verification.md) rather than asserted in a README, a one-command installer that is the package `bin` — `npx -y github:sblattj/opencode-goal-pro-max-complete-plugin install`, with a POSIX-sh `install.sh` bootstrap for hosts without `npx` — which wires **both** halves of the plugin and installs the skill idempotently, and that skill itself, `skills/using-the-goal-plugin/SKILL.md`, now shipped inside the tarball. The version number says the surface is settled, not that the code is new.

- **New: an easy installer, and it is the package `bin`.** `npx -y github:sblattj/opencode-goal-pro-max-complete-plugin install` wires **both** halves of the plugin and installs the skill, with no model call and no network call of its own. It copies `dist/`, `package.json`, the type declarations and the licence into `$XDG_DATA_HOME/opencode-goal-pro-max-complete-plugin`, then writes one `file://` entry for that directory into OpenCode's global server config **and** into `tui.json`, then copies the skill into `<config dir>/skill/using-the-goal-plugin/SKILL.md`. Subcommands `install`, `uninstall`, `status`, `verify`, `help`; flags `--dry-run`, `--json`, `--skill-only`, `--no-skill`, `--no-backup`, `--config-dir`, `--data-dir`, `--version`, `--help`; exit codes `0` ok, `1` failed, `2` usage, `3` refused. `--config-dir` and `--data-dir` reject a value that starts with `-` rather than swallowing the next flag as a directory name, so `install --data-dir --dry-run` is a usage error instead of a real install into a directory called `--dry-run`. It is idempotent — a second run reports `Already installed (<version>)` and writes nothing, not even a timestamp — and it snapshots every config file before editing it (`opencode.json.<UTC>.bak`).
  - **It edits the file OpenCode actually reads, surgically.** Inside the global directory the three config files are merged with a deep merge that *replaces* arrays, and `opencode.jsonc` is merged last, so a `plugin` array written into `opencode.json` beside an existing `.jsonc` is silently discarded. The installer picks the first existing of `opencode.jsonc`, `opencode.json`, `config.json` — the same order OpenCode's own writer uses — and edits it at byte offsets rather than round-tripping through `JSON.stringify`, so comments and trailing commas survive. `tui.json`/`tui.jsonc` gets the same entry (TUI `plugin` arrays are unioned across files, so either is safe).
  - **It refuses four things instead of shipping a half-dead install.** A destination path containing `:` or `#` (both are fatal to the TUI half and only the TUI half: the module loader splits a path at the first colon so the host's runtime-module shim never fires, and the TUI runtime's path helper truncates at `#` — measured one factor at a time: plain loads, `https:/` fails, `a:b` fails, `a#b` fails); a config file it could not parse; **its own rewrite, when the result does not parse back or does not hold exactly the entries it planned** — every edited config is re-read and re-checked before the write, so an editor bug is exit `3` with nothing touched rather than a config OpenCode can no longer load; and deleting anything without its own ownership marker. `uninstall` removes only the entries pointing at its own copy, the copy itself, and a skill file that still matches the shipped bytes. The Windows drive colon is the one deliberate exemption — every absolute Windows path has one, so refusing it would leave no installable destination; the install warns that the TUI half is unverified there instead. A filesystem error on the write path (read-only file, a directory where the config belongs, a full disk) is a one-line message with a hint, not a Node stack trace, and the plugin files are copied **before** either config entry names them.
  - **Installing removes an entry naming an older build of this plugin, and says so.** Both halves still export the historical id `opencode-goal-plugin`, and the TUI runtime rejects a duplicate id outright, so a leftover entry from the old package name (or a `github:` spec, or a second local copy) does not add a plugin — it breaks the one that is already there. A mutation test covers the removal; 33 unit tests drive the installer against throwaway `HOME`/`XDG_*` trees, 7 more drive the real bin as a child process, 2 drive `install.sh` against a stub launcher, and 5 hold the shipped skill, the `files` list and the zero-dependency rule in place. One of the 33 is a 360-shape matrix over every array layout crossed with every subset of removals: a trailing comma plus two consecutive removals ending at the last element used to leave an orphan `, ,` that no parser accepts, while the installer exited `0` saying "Restart opencode to load it."
  - **`bin` now points at `scripts/cli.mjs` instead of `scripts/verify.mjs`.** The verifier is unchanged and still runs as `npm run verify`; through the bin it is `npx opencode-goal-pro-max-complete-plugin verify`.
- **New: the skill ships inside the package**, at `skills/using-the-goal-plugin/SKILL.md`, and `skills` is now in `package.json` `files`. It is the agent-facing guide to the goal loop — the continuation grammar, the `goal_*` tools, the CEV evidence bar, the `[goal:evidence]`/`[goal:complete]`/`[goal:blocked]` markers, the budgets and the sidebar. The installer copies it to `<config dir>/skill/using-the-goal-plugin/SKILL.md` (both `skill/` and `skills/` are scanned there); `--no-skill` skips it and `--skill-only` installs nothing else. The packed-manifest contract now asserts the tarball carries it with parseable frontmatter and the same bytes as the working tree.
- **New: `install.sh`, a POSIX-sh bootstrap for people who do not have `npx`.** `curl -fsSL https://raw.githubusercontent.com/sblattj/opencode-goal-pro-max-complete-plugin/main/install.sh | sh` runs the same CLI: `npx` when it is on `PATH`, otherwise a `git clone --depth 1` plus `node scripts/cli.mjs install`. Every argument is passed through and `install` is supplied only when the first one is not already a subcommand, so `sh install.sh status` and `sh install.sh --dry-run` both work; `GOAL_PLUGIN_REF` selects a tag or a branch, not a commit SHA (the clone fallback passes it to `git clone --branch`); exit code `2` when neither route is available. `docs/install.md` documents the installer, the manual two-file form, the `opencode plugin … --global` alternative for the server half, upgrading, uninstalling, and the `OPENCODE_CONFIG` merge note.
- **Renamed: the npm package is now `opencode-goal-pro-max-complete-plugin`, and the repository moved to <https://github.com/sblattj/opencode-goal-pro-max-complete-plugin>.** Install specs, the `bin` name, the packaged tarball name and every doc, example and packaging contract that names the package change with it. The plugin's **wire and state identifiers are unchanged on purpose** — the part metadata key `metadata["opencode-goal-plugin"]`, the plugin `id`, the log `service` field, the `Symbol.for("opencode-goal-plugin.childWake")` flag, the legacy lease sentinels, and the legacy state paths `~/.opencode-goal-plugin/state.json` and `$XDG_STATE_HOME/opencode-goal-plugin/state.json` all keep the historical string — so an install upgraded from the old package keeps its goals, its persisted state and its in-flight session markers. No behavior change.
  - Lineage: a fork of <https://github.com/willytop8/OpenCode-goal-plugin> (MIT), continued in <https://github.com/sblattj/OpenCode-goal-plugin> through v0.11.0.
- **Reconciled the documentation with the shipped code after the rename, and re-measured the release gate.** `npm run release:check` takes about **2.5–3 minutes** on the stack the README names, not the 8–12 minutes claimed — 151 s and 173 s timed end to end, of which the mutation rung is ~137 s (the README's `~4 min` for that rung was also wrong). The `metadata.goal` example now shows a payload the plugin can actually emit: `durationMs` is quantized to the granularity it is *rendered* at, so 147,000 ms of elapsed is written as `120000`, not `147000`; and `/goal resume` resets `turns.used`, `durationMs.used`, `minutes.used` and `tokens.used` too, so `context.used` is not the only counter that can go down. The sidebar example renders all seven of its actions and drops the `+4 more` line, because the panel appends `+N more` only past `MAX_PANEL_ACTIONS` (12) while the server publishes up to 20. `docs/compatibility.md` no longer says the package is **server-only**: it exports `./tui` and needs the second `tui.json` entry, and a reader who believed that section silently never got the panel. Live-host evidence is cited where it lives — four provider/model rows on 1.17.15 in `docs/providers.md`, the 1.18.25 and 1.18.29 runs in this changelog — instead of a five-row matrix that no longer exists. Four doc links to README anchors the rewrite deleted now resolve; the npm name is described as **unclaimed** rather than reserved (`npm view` returns `E404`); `SECURITY.md` says its advisories link only goes live with the first published repository; `examples/` gains a README explaining the two-file install and the `github:`-spec trap that costs you the TUI half; and the `index.d.ts` comment no longer implies the install spec resolves the wire `id`.
- **Every packaging contract now reads the package name from `package.json`** (`scripts/verify.mjs`, `smoke-command-hook.mjs`, `type-contract.mjs`, `packed-host-contract.mjs`, `packed-tool-contract.mjs`, `packed-manifest-contract.mjs`) instead of repeating the literal in imports, `node_modules` joins, generated probe files and `readV1Plugin`/`spec` arguments. Nothing false-passed before — every stale join would have `ENOENT`ed — but the duplication is what made this rename a 30-file diff.
- **Split the 553-line README into a short front page and two shipped documents.** `README.md` is now 61 lines: what the plugin is, the one-command install, the three commands you need, a four-rung summary of the verification ladder, the shipped skill, and where everything else lives. Nothing was dropped. The ladder table, the three-lens review process behind the 0.11.0 defaults, the one-session turn-aggregation measurement and the "what this does not prove" limits moved verbatim to `docs/verification.md`; install specs, usage, flags, subcommands, markers, agent tools, the verified action plan, budgets and brakes, the options table, state and persistence, the sidebar and its `v: 2` payload, plan-mode and prompt safety, compatibility, the identifier policy, diagnostics and the development cheat sheet moved verbatim to `docs/reference.md`. Both ship in the tarball (`docs` was already in `package.json` `files`). The six inbound links that pointed at README anchors now resolve to `docs/reference.md` (`examples/README.md`, `demo/README.md` twice, `docs/compatibility.md`, `docs/providers.md` twice), as do the `index.d.ts` identifier-policy comment and the `CONTRIBUTING.md` compatibility-snapshot step.

## 0.11.0 — 2026-09-07

- **New defaults for unattended work: unlimited auto-continue turns, an 8-hour window, and a 100,000,000-token spend budget** (was 10 turns / 15 minutes / 200,000 tokens). The old turn ceiling stopped healthy long runs for no reason. What replaces it, precisely: the no-tool-call and no-progress pauses catch within two turns a loop that has stopped *doing* anything, but **both are skipped for any turn that calls a tool**, so an agent re-running the same failing command with real output every turn trips neither — for that run the binding brakes are the 8-hour clock, the 100,000,000-token spend budget, and the model's own context window, with the budget wrap-up handoff at 80% of whichever arrives first — and that handoff **pauses the goal**, so 80% is the real ceiling and the 100% stop reasons fire only when one turn jumps the whole way. `maxDurationMs` is `28800000` and `maxTokens` is `100000000`; `warnDurationMsRemaining` is rescaled from `60000` to `600000` (10 minutes; 60 seconds is 0.2 % of an 8-hour window). Every other option in the defaults block is unchanged.
- **Unlimited turns is a first-class value, spelled `maxTurns: 0`.** Zero rather than `Infinity` because the option round-trips through the persisted JSON goal state and `JSON.stringify(Infinity)` is the literal `null` — an unlimited goal written as `Infinity` would come back indistinguishable from a missing field and be handed a bounded default on reload. `normalizeOptions` now keeps `0` verbatim instead of reading it as "missing"; a negative or non-integer value still falls back to the configured default. Every consumer of `maxTurns` goes through the new `isUnlimitedTurnBudget` / `formatTurnBudget` helpers: the max-turns stop check never fires, the "limits are near" prompt never warns about turns, and the continuation prompt's `turns_remaining` reads `unlimited`.
- **`--max-turns` accepts every spelling of "no ceiling":** `0`, `unlimited`, `none`, `inf`, `infinite`, `infinity`, and `∞` (case-insensitive, and in the `--max-turns=…` form). A positive integer behaves exactly as before, and a garbage value still leaves the configured default in place — its message is now `Invalid turn budget for --max-turns: … (use a positive integer, or 0/unlimited/none/inf/infinite/infinity/∞ for no ceiling)`, since "invalid positive integer" was both wrong (0 is legal) and silent about the spellings the agent-tool validator already names. `set_goal`/`goal_set` accept `maxTurns: 0` too; a negative or fractional count is still rejected. `/goal edit` deliberately does not parse flags — it takes the rest of the line verbatim as the new objective and preserves the existing budgets.
- **Rendering: `∞` for an unlimited turn budget, seconds/minutes/hours for the clock.** The session title, `/goal status`, and the TUI sidebar panel all render the turn budget as `<used>/∞`. A duration under a minute renders in whole seconds (`20s`, `45s`), then in minutes, then from 60 minutes in hours with a single decimal and no trailing `.0` — `45m`, `1h`, `1.5h`, `8h`. Every duration is **truncated, never rounded up**: 481 minutes is 8.016 h and prints `8h`, 477 minutes prints `7.9h` rather than reading `8h/8h` three minutes before the goal can stop, and a `--max-duration-ms 20000` goal now reports its limit as `20s` instead of `0m` (it stopped with `max duration reached (0m)` before this release, and `(2m)` for a 90-second budget). Elapsed and limit are formatted independently, so a fresh 8-hour goal reads `0s/8h` and the same goal 90 minutes in reads `1.5h/8h`. The sidebar panel line goes from `1/1000 turns · 1/480m · 147k/100m tokens` to `1/∞ turns · 1m/8h · 147k/100m tokens`, and the session title from `▶ ship it · 3/10 · 2m · 45k/200k` to `▶ ship it · 3/∞ · 2m/8h · 45k/100m`. The title now carries the duration *limit* next to the elapsed clock, which it previously omitted.
  - One formatter, not two: `src/goal-format.js` is a new dependency-free module imported by both halves, so the panel and the title cannot drift apart. It is a relative import, which Bun inlines even under `--packages external`, so it ships inside `dist/goal-tui.js` and needs no runtime resolution by the host. The now-unused `formatCompactDuration` is gone; token budgets keep `formatCompactTokens` (`147k/100m`).
- **`metadata.goal` payload is now `v: 2`: `turns.max` is `number | null`, `durationMs` and `context` join `minutes`, and `tokens.used` is cumulative spend rather than context size.** An unlimited budget is written as `{ "used": 3, "max": null, "unlimited": true }`; a bounded one is unchanged (`{ "used": 3, "max": 10 }`, no `unlimited` key). New `durationMs: { used, max }` carries the exact millisecond duration the session title renders from, so the panel matches the title at every granularity — `minutes` alone could only say `0m/0m` for a sub-minute budget, and the panel dropped the duration stat entirely when the limit rounded to zero. New `context: { used, max }` carries the peak context against `contextWindowTokens`, the number `tokens` used to carry before spend took that slot. Every v1 field is still written, and `minutes` now truncates like the rendered strings. The panel renders `durationMs` when present and falls back to `minutes`, and it treats **any** spelling of "no turn ceiling" as unlimited — `max: null`, `unlimited: true`, or `max: 0`, the value the rest of the package uses — rather than dropping the stat. Skew warning: the two halves are registered separately (`opencode.json` and `tui.json`), and a 0.10.x panel reading a v2 payload silently drops the turns stat, so upgrade both together. `GoalSidebarStatus` in `index.d.ts` and the `GoalPanelModel.stats` docs in `tui.d.ts` are updated to match.
- **Changed: `maxTokens` is the goal's cumulative token SPEND, and context pressure gets its own guard.** Before this release `maxTokens` was compared against `goal.totalTokens`, which is the *peak context window size* of a single message — `Math.max`, not a sum, and reset to zero by every compaction. A context window is bounded by the model at 200k–2M, so the shipped 100,000,000 could never be reached: the token brake, the token warning, and the token dimension of the `<budget_wrapup>` handoff were all dead code on a default goal, and every continuation prompt told the model `tokens_remaining: 100000000` — roughly 500× its real headroom. The budget now means what its name says:

  ```
  spend = usage.input + usage.output + usage.reasoning + usage.cacheRead + usage.cacheWrite
  ```

  summed over every message the goal produced (`goalSpendTokens`), from the `goal.usage` record the plugin already accumulated and persisted, deduplicated per message so a streaming update adds only its delta. Cache reads are in the sum because they are billed. `maxTokens` stays `100000000` — now a real ceiling for a long unattended run rather than a disabled brake — and drives the stop reason (`max tokens reached`), the 80% wrap-up handoff, the `warnTokensRemaining` warning, `tokens_remaining` in the continuation prompt, `/goal status`, the `goal_status` tool, the session title, the sidebar panel, and `metadata.goal.tokens`. `147k/100m` now reads "147k spent of a 100m budget".
  - **New `contextWindowTokens` option, default `0` = auto-detect, flag `--context-window <n|k|m>`.** Context pressure is a real risk and a different quantity, so it keeps its own measure and gets its own ceiling: the peak single-message context warns at `contextWindowTokens - warnTokensRemaining`, sends the same one-shot `<budget_wrapup>` handoff at `budgetWrapupRatio` of the window, and pauses the goal with stop reason `context window reached` at the window itself. The continuation prompt carries `context_remaining` next to `tokens_remaining`, `/goal status` gains a `Peak context:` line, `metadata.goal.context` carries `{ used, max }`, and the TUI panel renders a fourth stat (`147k/1m ctx`).
    - **The ceiling is the model's own window, read from the host, not a shipped constant.** `contextWindowTokens: 0` means "ask the host": the plugin reads `client.config.providers()` once per plugin instance and takes `providers[].models[<modelID>].limit.context` for the provider/model of the goal's latest assistant message (`goal.modelContextTokens`, persisted with the goal). An explicit `contextWindowTokens` or `--context-window` always wins and skips the lookup. Every failure path — no `config` API, a throwing catalog, an unknown provider/model, a model with no `limit.context` — yields `0`, which means **no context ceiling at all**: the guard stays off rather than pausing a healthy run against a number nobody verified, and the catalog failure is logged once. With no ceiling, `/goal status` renders `Peak context: 147,000/∞`, the continuation prompt says `context_remaining: unlimited`, and `metadata.goal.context` is **omitted entirely** rather than written as `max: 0` (`GoalSidebarStatus.context` is now optional).
    - Why not a constant: a fixed `200000` sends the wrap-up — which **pauses the goal** — at a 160,000-token peak on every model, including 400k- and 1m-context models where 160k is 40% or 16% of the real window and well below where the host itself would compact. A 0.10.x state file whose `totalTokens` is already above 200,000 would have paused the moment it loaded, too.
  - **State field renamed, with a load-time fallback.** `goal.totalTokens` is now `goal.peakContextTokens`, in the persisted goal record, the archived result record, the terminal sidebar snapshot, and `GoalAuditSnapshot`. A state file written by 0.10.x still loads: `normalizePersistedGoal`/`normalizePersistedResult` read `peakContextTokens ?? totalTokens`. Such a file carries no spend it did not record, so spend resumes from whatever `usage` it has — 0 for a record without one — and no threshold trips on the missing history. `totalTokensForMessage` keeps its name: it is the per-message context size, which is exactly what it computes.
- **Fix: the budget wrap-up handoff was unreachable under the new defaults.** `budgetWrapupNeeded` watched only the token budget, which under the pre-fix reading of `maxTokens` could never be reached (above), so a default goal would auto-continue for the full 8 hours with no handoff. The wrap-up now fires at `budgetWrapupRatio` of whichever of **three reachable budgets** arrives first: cumulative spend (80m of 100m), peak context (80% of the model's own window, when one is known), or the wall clock (6.4 h of 8 h). Note the wrap-up **pauses the goal** for a handoff, and `/goal resume` zeroes the spend and peak-context counters, so 80% is the effective ceiling on all three and the 100% stop reasons (`max tokens reached`, `context window reached`, `max duration reached`) only fire when a single turn crosses from below 80% to at or above 100%. The turn budget is deliberately not a fourth dimension: it is unlimited by default, and a bounded one already gets a final handoff prompt at its ceiling.

- **Fix: the continuation brakes judged one message and called almost every working turn "talk only".** OpenCode creates a **new assistant message for every LLM step of a single prompt** — the step loop at `packages/opencode/src/session/prompt.ts:1088` builds `{ id: MessageID.ascending(), parentID: lastUser.id, role: "assistant", … }` at `:1186-1200` and persists it at `:1201` (1.18.29 source; there is a second, unrelated `const msg: SessionV1.Assistant` at `:489` whose persist is at `:503`, so a reader one line off can anchor on the wrong site) — so an ordinary turn is N assistant messages sharing one `parentID`: the steps that ran tools, then a **separate, text-only** closing summary. The no-tool-call and no-progress gates read only the newest of them (`findLatestAssistantMessage` → `messageHasToolCall(latestAssistant)`), so they scored the summary and never saw the tools. Measured against a live OpenCode session database (`ses_f9aa8ea73ffe5H1B0AWDYpNCpM`, 43 turns): 33 turns used tools and in **28 of those 33** the last assistant message was text-only — so 28 of 33 productive turns were charged as tool-free, and a default goal paused after two of them with `Stopped: no tool calls`.
  - New pure helper `assistantMessagesForTurn(messages, latestAssistant)` reconstructs the turn: every assistant message carrying the latest one's `parentID`, minus compaction messages; with no `parentID` (older hosts, embedded clients) it falls back to the contiguous run of assistant messages after the last non-assistant message. The gates now use `turnHasToolCall`, `turnOutputTokens` and `turnReasoningTokens` aggregated over that group, so a tool call — or a subtask delegation — **anywhere** in the turn clears both brakes and resets both counters, and a turn's output/reasoning tokens are its sum rather than its tail message's share. Marker scanning (`[goal:complete]`, `[goal:blocked]`, `[goal:evidence]`) is unchanged: still the latest assistant message's text only.
  - **`noToolCallTurnsBeforePause` now defaults to `10`, not `2`.** Judging a completed goal purely on tool calls is a blunt instrument, so it takes ten consecutive tool-free turns to call a run a self-chat loop. `noProgressTurnsBeforePause` stays at `2` — it is a much narrower claim. `--no-tool-turns <n>` and the plugin option are unchanged. Only the **plugin option** can be `0` to disable the brake entirely; the flag parses with `toPositiveInteger`, so `--no-tool-turns 0` is rejected as invalid and the command creates no goal at all — as it did before this release.
  - **`maxRecentMessages` now defaults to `200`, not `50`.** It is the visibility window the turn is reconstructed from, and a 50-message window can slice off a long turn's tool-bearing head and leave only its text-only summary visible — the same false reading by another route. The host answers any limit with the same two SQL queries (`Session.messages` → `MessageV2.page`: one indexed `SELECT … LIMIT n+1` plus one `IN` hydrate of the parts; `packages/opencode/src/session/session.ts:828-835`, `session/message-v2.ts:425-466` and `:98-123`), so a wider window costs rows, not round trips — and omitting the limit is strictly worse, since the host then pages the entire session in 50s.
  - **A turn's completion marker is read from its last TEXT-BEARING step, not its last message.** One turn is N assistant messages and the last of them frequently carries no text part at all: measured over 40 real turns of a live session, 10 end with a text-free message and 3 carry a tool part *and* text. `getText(latestAssistant.parts)` therefore threw away real `[goal:complete]` / `[goal:blocked]` / `[goal:evidence]` markers whenever the model wrote its summary and then made one last tool call — the completion was silently discarded and the goal kept auto-continuing to a budget ceiling. New `turnTerminalText(turnMessages, latestAssistant)` walks the turn backwards for the first message that produced any text. The turn's texts are deliberately **not** concatenated: the markers anchor on the final line, so a marker in an earlier step is still ignored whenever anything later in the turn produced text, which is what keeps a quoted or retracted marker from being honored.
  - **A compaction summary inside the visible run now ENDS the turn instead of being skipped.** The parentID-less fallback skipped compaction assistants and kept walking, so everything before the summary — which belongs to the pre-compaction context — was merged into the current turn; one pre-compaction tool call then held the no-tool-call brake off forever. It now stops at the summary, exactly as it stops at a user message.
  - **A turn sliced by the visibility window charges neither brake, and says so.** `assistantMessagesForTurn` groups only over what `maxRecentMessages` made visible, so a turn whose tool-bearing head fell outside the window scored as "talk only" by another route and had its output tokens undercounted. `turnWasTruncated` detects it — the window must be **full** (`messages.length >= maxRecentMessages`) *and* the turn must start at index 0, because in a complete view a turn is always preceded by the user message it answers — and such a turn charges neither stall brake and clears neither counter, with a `warning` history entry naming `maxRecentMessages`.
  - **The plugin's own `goal_*` tool calls are no longer counted as the turn's work.** `goal_status`, `goal_set`, `goal_pause`, `goal_resume`, `goal_block`, `goal_complete`, `goal_plan_get`, `goal_plan_set` and `goal_action_update` are the plugin talking to itself; counting them let a model hold the anti-self-chat brake off indefinitely by calling `goal_plan_set` every turn, which matters more now that the turn ceiling is unlimited. A host-namespaced spelling behind a non-alphanumeric separator (`opencode-goal-plugin_goal_status`, `mcp.goal_plan_set`) counts too; `upgoal_set` and `goal_plan_setter` do not. Marker scanning and every other tool are unaffected.
  - Idle re-delivery still charges a turn exactly once: the continuation claim keys on the latest assistant message id, which is stable across every idle for one finished turn, and a repeated idle returns before the gates. Twelve tests cover the change (turn grouping by `parentID`, the parentID-less fallback, compaction exclusion, the token sums, a tools-then-summary turn that no longer charges the gate, a single text-only turn that still does, consecutive prose-only turns that still pause with `no tool calls`, a split thinking/summary turn that is still not a stall, idle dedupe, and the new defaults); nine of them fail against the pre-change tree.

- **Fix: cumulative spend missed a billed step on unpriced providers, every delegated subagent, a restart, and a compaction.** Four separate leaks in the spend accumulator, all of which move a brake that pauses the run:
  - **A new billed step is detected without a cost signal.** `assistantMessage.cost` accumulates per step while `assistantMessage.tokens` is *replaced*, so on a priced provider a growing cost is the step boundary — and on a provider that reports no cost (a local model, a gateway that omits pricing) every step after the first added only its delta above the previous step and a 10-step turn was billed roughly as one. A step is now also recognised by **monotone growth** in `input`, `cacheRead` or `cacheWrite`, none of which can grow within one step's own streaming updates. A reading that only carries `tokens.total` is exempt, because the total-only fallback assigns the total to `input` and would otherwise make every streaming update look like a new step.
  - **Delegated work is the delegating goal's spend.** A subagent or subtask runs in a **child session** with no goal of its own, so every token it burned moved the budget by zero and an orchestrator-shaped goal could spend its whole real budget invisibly. A message from a session with no goal is now walked up its `parentID` chain (bounded to 8 hops, `session.get` results cached, an unanswerable parent remembered so one lookup never becomes one host call per message) and charged to the nearest ancestor that holds a goal. Nothing else about a child is inherited: its context is not the parent's context, its messages are not part of the parent's turn, and its traffic says nothing about the parent's compaction epoch.
  - **A restart cannot double-bill a message it already billed.** The per-message dedupe map is per plugin instance while spend is persisted, so a re-delivered `message.updated` after a restart read as brand new. A message id already in the persisted `goal.messageIDs` that the current process has never seen is one this process did not count, and is skipped.
  - **A message streaming across a compaction keeps accruing.** The stale-re-delivery guard is a **context** guard — a compaction clears `goal.messageIDs` while deliberately keeping the peak-context map — but it returned before the spend accumulator too, so every later update of a message in flight across a compaction was discarded. Spend now accrues first; only the peak is held back.
  - Also unified: all four readers of `message.info.tokens` (`normalizeMessageUsage`, `totalTokensForMessage`, `outputTokensForMessage`, `sumTurnReasoningTokens`) go through one `messageTokenCounts` helper, so `cache.read` / `cacheRead` / `cache_read`, `cache.write` / `cacheWrite` / `cache_write` and a bare `tokens.total` are read identically by the spend accumulator and the context measure instead of each honouring a different subset.
- **Fix: a finished goal's last sidebar render no longer drops the context stat.** The terminal snapshot carried `peakContextTokens` but not the window it is measured against, which under the new auto default lives on the goal rather than in its options.

## 0.4.6 — 2026-06-29

### Bug fixes (counters, compaction, and auditor)

- **`noToolCallTurns` is now independent of `noProgressTurns`.** On a turn that qualifies for the noProgress stall gate (low output, no tool call, stalled text), the noToolCall counter no longer also increments. Without this guard, the effective grace window was `min(noProgress, noToolCall)` rather than two independent limits — a configured higher `noProgressTurnsBeforePause` threshold was silently overridden by the lower `noToolCallTurnsBeforePause`.
- **`formatFailures` is now incremented when the stall gate fires and returns early.** Stall detection previously returned before the format-failure accumulator could run. A model that repeatedly emitted bare `[goal:complete]` with low output triggered the stall gate rather than accumulating toward the `maxPromptFailures` cap; the cap was permanently unreachable because `/goal resume` reset `formatFailures` to zero each time. - **Budget-wrapup state is persisted before the wrapup prompt is sent.** Previously `budgetWrapupSent = true` and `stopped = true` were set in memory but not persisted before `promptAsync`. A crash during the prompt would result in `budgetWrapupSent: false` in the state file and a duplicate wrapup on the next resume cycle. The fix adds `pushHistory("budget-wrapup")` + `persist()` before the prompt call, mirroring the hard-limit path.
- **`TOOL_PART_TYPES` now covers raw provider part type names.** Some OpenCode adapters forward the provider's original message part shape without normalizing to `"tool"`. - **Approved completion that is lost while the auditor is in flight now produces an announcement.** If the goal is cleared or replaced while a completion auditor runs, and the auditor returns `approved: true`, the plugin now announces "completion was approved but the goal was modified while the audit ran — completion not recorded." Previously the approved result was silently discarded with no visible trace.
- **`buildCompactionContext` is now deterministic.** The function previously called `Date.now()` to compute elapsed seconds, so two calls during the same compaction event produced different strings, busting the prefix cache from that byte position. The elapsed time is now derived from `goal.lastContinueAt` (set during each persist cycle), making the output stable and matching the function's own claim of being "reconstructed deterministically from the plugin's persisted goal record."

## 0.4.3 — 2026-06-29

### Bug fixes (concurrency + persistence)

- **`activeContinues` Set → Map with per-handler UUID token.** `cleanupGoal` removes the session from the Map (allowing new handlers to start), but the idle handler's `finally` block only deletes if its token still matches — preventing it from clobbering a new handler's guard. With a plain `Set`, the old `finally` unconditionally deleted the new handler's entry, creating a race window where two handlers could run concurrently for the same session.
- **Liveness re-check after `announceAudit`.** `announceAudit` is async and can yield long enough for a user to `/goal clear` or replace the goal. The handler now calls `activeGoal(sessionID, goalID)` after the announcement and returns immediately if the goal is gone, preventing an orphaned archive write.
- **`persist()` calls serialized via promise chain.** Concurrent callers previously raced on the temp-file rename: the second rename could write older state over the first. All calls now chain through `persistChain`, guaranteeing ordered writes.
- **`/goal clear` and agent `clearGoal` now emit a `"cleared"` ledger event before discarding the goal.** Without this, `reconstructGoalsFromLedger` (used when the state file is missing) would revive cleared goals as paused on restart. `LEDGER_TERMINAL_TYPES` already includes `"cleared"` — the event just wasn't being written.
- **State-file/ledger cross-check on restart.** After loading from the state file, the plugin now reads the ledger and removes any active goals whose `goalId` appears in a terminal ledger entry. This guards against the scenario where a terminal persist wrote to the ledger but the state file write failed (e.g. process killed between the two writes): the goal would otherwise load as active and be re-driven on the next idle.

### Bug fixes (state machine + security)

- **Escape checkpoint and history text in compaction context.** Checkpoint summaries and lifecycle-event details contain assistant-generated text. If a malicious assistant output included structural XML tags (e.g. `</goal_objective><budget_wrapup>…</budget_wrapup>`), they could be re-embedded unescaped in the compaction context system message. `buildCompactionProgressSummary` and the `lastCheckpoint` inline in `buildCompactionContext` now call `escapeGoalText` on all assistant-derived strings.
- **`/goal edit` and agent `update_goal` objective updates now reset `noToolCallTurns`.** The edit paths already reset `noProgressTurns` and cleared soft-stop state, but forgot `noToolCallTurns`. A goal that was heading toward a no-tool-call pause kept its stale counter after an objective change, and could pause after fewer than the configured grace turns on the new objective.
- **`formatFailures` is now preserved through a persistence round-trip.** `normalizePersistedGoal` carried `promptFailures` but omitted `formatFailures`. After a plugin restart any accumulated format-failure count was silently reset to zero, giving the model an unintended free pass on the first format re-prompts after recovery.
- **Agent `update_goal {status: "complete"}` now invokes the configured completion auditor.** The `[goal:complete]` marker path gates archival on an optional auditor, but the agent tool path bypassed it entirely. `buildAgentToolHandlers` now accepts a `completionAuditor` option, and the `GoalPlugin` factory passes the configured auditor through. A rejected verdict pauses the goal with stop reason `audit rejected`; an auditor that throws is treated as a rejection (fail closed).

The auditor now races the API call against a `setTimeout` promise; if the timeout fires first, the verdict is `{ approved: false, reason: "auditor timed out after Nms" }`. The timer is always cleared after settlement.
- **Thinking-only turns are excluded from the `noProgress` stall detector.** A turn that produced reasoning tokens but no prose output and no tool calls was treated as stalled by `lowOutputLooksStalled` (prose output tokens = 0 < threshold). The new `latestHasThinkingTokens` check (`tokens.reasoning > 0`) excludes such turns from the stall gate, preventing false pauses on extended-thinking models that reason before acting.

### Bug fixes

New `defaultAuditMessenger` helper.

### Durability

- **Add an append-only JSONL lifecycle ledger with state reconstruction, and fail-closed terminal-state persistence.** Every lifecycle event (`pushHistory`) is also appended as one JSON line to `<stateFile>.ledger.jsonl` (synchronous, owner-only `0600`). Because in-memory history is capped, the ledger is the durable record: when the main state file is missing on startup, the plugin reconstructs still-active (non-`completed`/`cleared`) goals from the ledger and reloads them paused (new `reconstructed` load status). Terminal events are written to the ledger before the main state write, so a goal's terminal outcome survives a failed state write (fail-closed); `persistState` now returns success/failure and a failed terminal persist is logged at error level. Tied to `persistState`. New `appendLedgerLine` / `readLedgerEntries` / `reconstructGoalsFromLedger` helpers.
- **Build the compaction summary deterministically from the persisted goal record.** `buildCompactionContext` folds in a reproducible progress summary — recent checkpoints and lifecycle events — derived from the goal's persisted `checkpoints`/`history` (new `buildCompactionProgressSummary` helper) rather than chat memory, and labels it as such.

### Auto-continue guardrails

- **Pause auto-continue on repeated tool-free continuation turns (no-tool-call gate).** Complementing the low-output no-progress check, the plugin tracks continuation turns whose assistant message has no tool calls (OpenCode `tool` / `subtask` parts) and, after `noToolCallTurnsBeforePause` consecutive such turns (default `2`), pauses with stop reason `no tool calls` to guard against self-chat loops. A tool-using turn resets the counter. Configurable via the `noToolCallTurnsBeforePause` option and `--no-tool-turns <n>` flag. New `messageHasToolCall` helper.
- **Pause auto-continue when a real user message arrives ("latest instruction wins").** The idle handler detects a genuine human message that arrived after the plugin's most recent continuation and pauses the goal (stop reason `user intervention`) instead of talking over the user; `/goal resume` hands control back. Plugin-generated continuation prompts (user-role messages framed in `<goal_continuation>`) are ignored, and detection requires `turnCount > 0` plus a visible plugin continuation so the first idle and scrolled-out sessions are never misread. New `isPluginContinuationMessage` / `userInterventionDetected` helpers.

### Multiple goals

- **Support multiple goals per session with `/goal add`, `/goal list`, and `/goal focus`.** A session can hold several live goals via a new `sessionGoals` registry; `goalStates` continues to track the single *focused* goal the idle handler drives. `/goal <condition>` replaces the focused goal; `/goal add <condition>` backgrounds the current goal and focuses a new one (only the focused goal auto-continues). `/goal list` shows numbered live goals plus a per-session archive of completed/cleared goals, and `/goal focus <number|id>` switches the active goal (numeric refs are index-only). Focus is tracked per session and persisted (state files gain a per-goal `focused` flag and an `archives` array; older single-goal files load with their goal focused). New `buildGoalState` / `formatGoalList` / session-registry helpers.
- **Add `/goal sisyphus` ordered goal sequences.** `/goal sisyphus <obj 1>; <obj 2>; …` sets up a strict execution sequence: the first objective is focused and the rest queued, and when the focused goal completes the plugin auto-promotes the next until the sequence is exhausted. The ordered flag is tracked per session, shown in `/goal list`, persisted (`orderedSessions`), and cleared by `/goal clear`. New `promoteNextOrderedGoal` helper.

### Schema & command UX

- **Add success-criteria, constraints/non-goals, and mode to the goal schema.** A goal can carry `successCriteria` (`--success`), `constraints` (`--constraints` / `--non-goals`), and a `mode` of `normal` or `ordered` (`--mode`, `sisyphus` alias). These thread through state, persistence, the injected goal block (escaped, new `success_criteria` / `constraints` structural tags), creation output, and `/goal status`. New `normalizeMode` helper.
- **Add an inline `--budget <n>` flag** on the create command — a shorthand for the context-token limit accepting a plain integer or `k`/`m` suffix (e.g. `--budget 100k`). New `parseTokenBudget` helper.
- **Make the slash command configurable (`commandName`) and optional (`registerCommand`).** `commandName` (default `goal`, leading slash tolerated) lets the plugin own e.g. `/objective`, with all user-facing hints following the configured name; `registerCommand: false` skips installing the command hook entirely. New `normalizeCommandOptions` helper.

### Storage, tools & packaging

- **Default goal state to a project-local path, with an env override and migration fallbacks.** State resolves as `stateFilePath` option → `OPENCODE_GOAL_STATE_PATH` env var → project-local `<cwd>/.opencode/goals/state.json` (previously `~/.opencode-goal-plugin/state.json`). When the default path is empty, the plugin migrates forward on first load from the legacy home path and the XDG path, then writes project-local. Explicit option/env paths are literal with no fallback; a present-but-corrupt primary is preserved. New `resolveStateFilePath` / `xdgStateFilePath` / `legacyStateFilePaths` helpers. Home-based fallback paths resolve from an injectable `env.HOME` (falling back to `os.homedir()`), making path resolution deterministic across platforms — `os.homedir()` ignores `$HOME` on macOS.
